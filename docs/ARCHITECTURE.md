# معماری پروژه

## ۱. اجزای سیستم

```
مرورگر
  │
  ├─ React SPA (Vite, RTL)               src/
  │    └─ fetch → /api/*  (کوکی نشست)
  │
  └─ پروکسی توسعه Vite ──► Express API (server/src) ──► PostgreSQL
                                │
                                └─ فایل‌ها: /app/uploads (سرو در /uploads/*)
```

- **تک‌مبدأ در توسعه:** مرورگر فقط با پورت ۳۰۰۰ صحبت می‌کند؛ Vite مسیرهای `/api`، `/uploads`،
  `/sitemap.xml` و `/robots.txt` را به سرویس `api` پروکسی می‌کند. به همین دلیل کوکی نشست
  same-site است و نیازی به CORS نیست.
- **در استقرار مستقل:** یک reverse proxy (Nginx/Caddy) همین نقش را بازی می‌کند (نمونه در
  `docs/DEPLOYMENT.md`).

## ۲. جریان درخواست

1. `src/lib/site.jsx` در بارگذاری اول `GET /api/site` را می‌خواند و تنظیمات، حوزه‌های فعالیت، سه
   پروژه اخیر، سه مقاله اخیر، آمار شفافیت و فهرست علاقه‌مندی‌های داوطلبی را در Context نگه می‌دارد.
2. صفحات فهرست/جزئیات مستقیماً از `useResource` استفاده می‌کنند (`src/lib/useResource.js`).
3. هر صفحه با `useSeo` عنوان، توضیح متا، canonical و JSON-LD خودش را تنظیم می‌کند. عمداً هیچ نقش
   سراسری عنوان وجود ندارد تا عنوان هر صفحه یکتای خودش بماند.
4. پنل مدیریت با `AuthProvider` وضعیت نشست را از `GET /api/auth/me` می‌خواند؛ مسیرهای `/admin/*`
   بدون نشست به `/admin/login` هدایت می‌شوند. **این فقط لایه ظاهری است؛ همه تصمیم‌های دسترسی در
   سرور با `requireAuth` / `requireRole` گرفته می‌شود.**

## ۳. لایه سرور

| فایل | مسئولیت |
| --- | --- |
| `index.js` | میدل‌ور عمومی، هدرهای امنیتی، سرو فایل، `robots.txt` و `sitemap.xml`، سوارکردن روترها |
| `db.js` | Pool اتصال، اجرای `schema.sql` در هر بوت (idempotent)، داده‌های اولیه |
| `auth.js` | امضا/بررسی JWT، کوکی نشست، `requireAuth`، `requireRole`، `canWrite`، `adminOnly` |
| `audit.js` | `logEvent` و میدل‌ور `auditMiddleware` برای ثبت تغییرات پنل |
| `payments.js` | آداپتور زرین‌پال و تشخیص حالت شبیه‌سازی |
| `routes/public.js` | محتوای عمومی، فرم‌ها، جریان کمک مالی، صفحات، محدودیت نرخ |
| `routes/auth.js` | ورود/خروج/من، تغییر رمز، محدودیت تلاش ورود |
| `routes/admin.js` | CRUD همه محتواها + کاربران، رسانه، گزارش رویداد، پشتیبان |

### سطوح دسترسی

| نقش | خواندن پنل | تغییر محتوا/رسانه | کاربران، تنظیمات، رویدادها، پشتیبان |
| --- | --- | --- | --- |
| `admin` | ✅ | ✅ | ✅ |
| `editor` | ✅ | ✅ | ❌ (403) |
| `viewer` | ✅ | ❌ (403) | ❌ (403) |

اعمال در `routes/admin.js`: یک میدل‌ور سراسری، هر متد غیر GET را با `canWrite` می‌سنجد؛ مسیرهای
حساس با `adminOnly` جدا محافظت می‌شوند.

## ۴. جریان کمک مالی

```
/donate  ──POST /api/donations──►  رکورد pending + کد پیگیری
   │                                   │
   └──────► /donate/checkout/:tracking ◄┘
                 │  POST /api/donations/:tracking/simulate   (بدون درگاه واقعی)
                 ▼
            /donate/result/:tracking   → وضعیت paid + برچسب «شبیه‌سازی‌شده»
```

- اگر `PAYMENT_GATEWAY=zarinpal` و `PAYMENT_MERCHANT_ID` تنظیم شده باشد، پاسخ `mode: gateway` است و
  کاربر به درگاه می‌رود؛ در این حالت مسیر شبیه‌سازی با 409 رد می‌شود.
- پرداخت شبیه‌سازی‌شده همیشه `simulated = true` می‌گیرد و در همه محاسبات عمومی (مجموع کمک، درصد
  پروژه، آمار شفافیت) کنار گذاشته می‌شود.

## ۵. تصمیم‌های طراحی

- **بدون آمار ساختگی:** هر عددی که در سایت دیده می‌شود از پایگاه داده می‌آید؛ مقدار خالی به
  «اطلاعات در حال به‌روزرسانی است» تبدیل می‌شود.
- **داده نمونه علامت‌دار:** ستون `is_sample` روی پروژه‌ها، مقالات و گزارش‌ها، برچسب «داده نمونه» را
  در کارت و صفحه جزئیات فعال می‌کند.
- **هنر گرافیکی به‌جای عکس بدون مجوز:** `src/components/Art.jsx` وقتی تصویر واقعی ثبت نشده باشد،
  طرح نمادین تولید می‌کند؛ بنابراین سایت هرگز عکس نامرتبط یا بدون رضایت نمایش نمی‌دهد.
- **محتوای متنی، نه HTML:** متن‌های پنل با `RichText` (پاراگراف، `## تیتر`، `- فهرست`) رندر می‌شوند و
  هرگز به‌صورت HTML تفسیر نمی‌شوند؛ این کار XSS ذخیره‌شده را حذف می‌کند.
- **یک‌مبدأ:** جلوگیری از پیچیدگی CORS و کوکی cross-site؛ در استقرار مستقل هم با reverse proxy حفظ
  می‌شود.
